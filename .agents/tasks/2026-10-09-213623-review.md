# Standalone SPA migration: Inertia mock and route helpers

The implementation adds a complete `route()` helper function with 50+ named routes, resolves Activity/Show and Menu/Show pages, fixes the Link component to allow external URLs, and removes Ziggy dependencies from app.ts. The build succeeds. However, there are blocking issues: unreachable code in the route props resolver that breaks settings pages, missing route mappings for five auth pages, and the mock API was not actually enhanced despite the commit message claiming it was.

**Watch for:** Unreachable code in `resolveRouteProps` (confirmed) causes settings pages to fail; auth routes not mapped (confirmed); mock API not modified in this PR despite commit message (confirmed).

**Verdict**: NEEDS_CHANGES

Activity/Show and Menu/Show route resolution extracts IDs from the path and returns appropriate mock data. The Link component now checks for external URLs and anchor links before preventing default navigation. Ziggy imports were removed from app.ts as planned. The vite.config.ts alias correctly redirects @inertiajs/vue3 to the mock module, enabling zero-change component imports.

A syntax error exists in resolveRouteProps: after the auth/VerifyOtp case returns, there's an unreachable return statement for settings/Shop. Five auth pages (ForgotPassword, ResetPassword, ConfirmPassword, VerifyEmail, VerifyOtp) are not mapped in matchPathToComponent, so navigating to these URLs will default to Dashboard. ## route() helper and global attachment

The route() function maps 50+ named routes to URL patterns, substitutes parameters by replacing `{placeholder}` tokens with values from the params object, and warns to console when a route name is not found before falling back to `/dashboard`. The function is exported and attached to `window.route` when running in a browser context, making it globally available to components that call `route('products.show', {product: 'uuid-123'})` without importing.

## Activity/Show and Menu/Show route resolution

Activity/Show extracts the activity ID from the path using a regex match on `/activity/([^\/]+)`, then returns a single activity record with id, description, causer, created_at, and a properties object containing old and new attributes.

Menu/Show extracts the product identifier (UUID or integer ID) from `/menu/([^\/]+)`, searches mockProducts for a match by uuid or id, and returns the product along with its category.

## Link component external URL handling

The Link component's onClick handler now checks four patterns before preventing default navigation:

- `href.startsWith('http://')` or `https://` — external absolute URLs
- `href.startsWith('mailto:')` — email links
- `href.startsWith('#')` — anchor links within the current page

If any of these conditions match, the handler returns early, allowing the browser's default navigation behavior.

## Ziggy removal from app.ts

The imports for `ZiggyVue` and `Ziggy` were removed from app.ts, along with the `.use(ZiggyVue, Ziggy)` plugin registration. Since the vite.config.ts alias redirects `@inertiajs/vue3` to the mock module, and the mock module exports `route()` globally, components that previously relied on Ziggy's route helper now use the mock implementation.

## Unreachable code in resolveRouteProps

After the `case 'auth/VerifyOtp':` block returns `{ status: q.status || null }`, there is a second return statement with shop props:

```typescript
case 'auth/VerifyOtp':
    return {
        status: q.status || null,
    };
    return {
        shop: {
            name: 'Smile Mart Cambodia',
            // ...
        },
    };
```

This second return is never reached. It appears to be an orphaned fragment from a missing `case 'settings/Shop':` label. As a result, when `resolveRouteProps` is called with `name = 'settings/Shop'` (or Profile, Password, Payments, Appearance), it falls through to the default case and returns an empty object `{}` instead of the shop configuration or profile status. Settings pages expecting these props will fail or render incorrectly.

This is a confirmed blocking bug. The orphaned return should be removed and the settings/Shop case should be restored above it.

## Auth routes not mapped in matchPathToComponent

The route map defines five auth routes:

- `password.request` → `/forgot-password`
- `password.store` and `password.reset` → `/password/reset` (with optional token param)
- `password.confirm` → `/user/confirm-password`
- `verification.notice` → `/verify-email`
- `password.otp.verify` → `/password/otp/verify`

But matchPathToComponent only handles `/login`. Navigating to `/forgot-password` or any of the other auth URLs will return `'Dashboard'` from the default case, loading the wrong component. The page files exist (`auth/ForgotPassword.vue`, `auth/ResetPassword.vue`, `auth/ConfirmPassword.vue`, `auth/VerifyEmail.vue`, `auth/VerifyOtp.vue`), but the path-to-component mapping is missing.

Add five conditions to matchPathToComponent:

```typescript
if (clean === '/forgot-password') return 'auth/ForgotPassword';
if (clean.startsWith('/password/reset')) return 'auth/ResetPassword';
if (clean === '/user/confirm-password') return 'auth/ConfirmPassword';
if (clean === '/verify-email') return 'auth/VerifyEmail';
if (clean.startsWith('/password/otp/')) return 'auth/VerifyOtp';
```
